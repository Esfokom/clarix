# Unified PDFium Editor Migration

## Goal

Make one long-lived PDFium document the authoritative source for an editor
tab. The same document must render visible content, expose physical page
objects, accept edits, and save the PDF. Rust provides semantic analysis,
transactions, undo/redo planning, and AI command validation; it does not open
or materialize a second PDF document.

## Current State

The viewer is rendered by pdfrx/PDFium. The editing UI is driven by the Rust
editor session and presents modified content through Flutter text and clean
patch overlays. PDFium text inspection and mutation utilities exist in Dart,
but they are not the document owner for the production editor. The resulting
split means a direct object mutation is not reflected in the visible pdfrx
page without a separate render path.

## Target Ownership

```text
Flutter UI
  -> Editor bridge / intent routing
  -> LivePdfiumSession (Dart, one PdfDocument per tab)
       render tiles, inspect, hit-test, mutate, commit, save
  -> Rust editing core
       semantic model, layout plans, transactions, validation, AI tools
```

`LivePdfiumSession` serializes every PDFium operation on pdfrx's owning
worker. No page, object, or font handle crosses worker boundaries. It owns
document disposal and rejects all requests after close.

## Interfaces

The native editing port gains a document-owner implementation exposing:

* `open(sourcePath)` — creates the live session and returns document metadata.
* `pageScene(page, revision, priority)` — returns semantic objects with stable
  IDs and physical PDFium locators.
* `renderTile(page, rect, scale, revision)` — returns BGRA/RGBA tile data from
  the live PDFium document.
* `apply(command, baseRevision)` — validates with Rust, resolves its locator,
  mutates PDFium, and returns an atomic revision acknowledgement.
* `commit(revision)` — completes any open same-page transaction and calls
  `FPDFPage_GenerateContent` before its `FPDF_PAGE` handle is released.
* `save(request)` — writes the already-regenerated live PDFium document
  through PDFium save APIs.
* `undo` and `redo` — replay inverse or forward commands against the live
  document, then invalidate affected tiles.

`EditorSceneObject` gains a physical locator field containing page number,
recursive object path, object type, source fingerprint, and object revision.
Semantic IDs remain UUIDs generated by the editor core. A locator is never
used as an AI-facing identifier.

## Command Flow

1. Flutter sends a manual or AI `PdfEditCommand` with its base revision.
2. Rust validates permissions, selection, text ranges, and layout/reflow
   requirements. It produces a physical edit plan and inverse plan.
3. Dart resolves physical object paths on the live document and applies the
   plan. A stale/missing path performs one page reinspection and rebind; a
   failed rebind rejects the transaction without mutation.
4. The session marks affected tiles and pages dirty, increments revision, and
   returns updated scene objects plus invalidated tile regions.
5. Flutter replaces only those regions with `renderTile` output. It does not
   paint replacement PDF text as the durable visual representation.
6. The currently bundled PDFium runtime requires content regeneration before
   the loaded `FPDF_PAGE` handle is closed; a later fresh page handle cannot
   reliably persist `FPDFText_SetText` changes. Same-page transactions may
   debounce this work, but single-object edits regenerate immediately. Saving
   then persists PDFium's document state; reopening must preserve the edited
   visual content.

## Rendering Migration

During migration, pdfrx continues to render untouched pages. A page with a
live edit receives dirty tile images from `LivePdfiumSession`, composited at
the page coordinate transform. When every page path has parity, switch all
tiles to the live session and retire the clean-patch plus Flutter replacement
text layers. Selection chrome, caret, handles, toolbars, and accessibility
remain Flutter overlays.

The tile cache key is `(document revision, page, scale, tile rect)`. A
revision change invalidates only tiles intersecting command-affected bounds;
zoom produces a new scale key. Tiles are bounded by an LRU memory budget and
may be regenerated safely.

## Command Migration Order

1. Whole single-text-object replacement using its existing font.
2. Text transform, fill, font size, and supported style changes.
3. Image/path transforms and object insertion/deletion.
4. Partial text-run replacement using object splitting and per-glyph geometry.
5. Multi-object lines, block reconstruction, and reflow.

Unsupported form-XObject/shared content, unsupported render modes, missing
fonts, and malformed geometry remain read-only with an explicit reason. Font
substitution is transactional: prepare an embeddable fallback before removing
any original object.

## Persistence and Compatibility

The Rust `clarix_pdf_adapter` remains available only as a controlled fallback
behind a compatibility feature flag while PDFium parity is established. It is
not used for commands already supported by `LivePdfiumSession`. The fallback
must serialize/reopen explicitly and cannot claim live rendering.

The existing editor command schema, approval flow, and AI tool API remain
stable. Their implementation changes from Rust materialization to physical
PDFium edit plans. Document revisions remain monotonic and command receipts
remain durable only after commit/save according to their existing contract.

## Error Handling

* Stale locator: reinspect once, rebind only if fingerprint and semantic text
  match, otherwise report a conflict.
* PDFium mutation failure: apply no remaining operations, restore previously
  applied operations from the inverse plan, keep prior revision.
* Tile render failure: retain the last valid tile and show a recoverable editor
  error; do not substitute a Flutter text overlay.
* Save failure: retain live edits and dirty-page set; preserve the existing
  save/recovery UI semantics.

## Verification

Unit and integration coverage must prove:

* physical-object text mutation changes a live PDFium-rendered dirty tile;
* only affected tile keys are invalidated;
* commit/save/reopen preserves edited text, searchability, and selection;
* undo/redo returns both scene metadata and raster output to the expected
  revision;
* stale locator, font failure, and unsupported-object edits are atomic;
* Flutter typing updates a page tile without closing or reopening the editor
  document.

Performance gates: visible-page mutation must never scan the full document;
initial edit mode indexes the visible page and nearby pages first; background
indexing is cancellable and cannot block typing or tile rendering.
